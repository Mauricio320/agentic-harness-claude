Versión 0.5.0 y las correcciones antes del piloto

Cómo funciona el arnés

Una explicación desde cero, para quien nunca ha visto un arnés ni sabe qué es un hook, un plugin o un mod. Todo lo que dice esta página sale del repo agentic-harness: el plan, el README, el CHANGELOG, los scripts y la prueba real del CRUD de talleres.

Las palabras raras van en negrita punteada la primera vez, con su explicación al lado. Todas quedan juntas en el glosario del final.

1

Qué problema resuelve, en tres frases

Claude Code es Claude trabajando dentro de tu terminal: lee tu código, lo edita y corre comandos. Un arnés es lo que le pones alrededor para que trabaje siempre igual, como el arnés de un escalador: no escala por él, pero no lo deja caerse.

  1. Que cualquier sesión, en cualquier proyecto, siga el mismo camino: plan, construir, verificar, revisar y entregar (en el repo se dicen plan → build → verify → review → ship), sin que tengas que acordarte de pedir cada paso.
  2. Que lo que tiene que cumplirse siempre no dependa de que Claude se acuerde: lo revisan programas que no piensan (lint, typecheck, tests, unos guardias y el CI, que es el servidor que vuelve a correr las comprobaciones cuando subes un cambio).
  3. Que en las zonas delicadas (migraciones de base de datos, autenticación, permisos) siempre haya una persona que revise antes de que el cambio entre.

Lo que NO hace

  • No sabe si tu cambio es correcto para el negocio. Sabe si compila, si pasa el lint, si los tests siguen en verde y si se respetaron las reglas escritas del repo.
  • No hace push ni abre merge requests por su cuenta: eso solo pasa si tú lo pides y dices que sí.
  • No reemplaza al CI ni a la aprobación en GitLab: las usa como garantía de verdad.
  • No trae nada del stack cableado: los comandos de cada proyecto los lee de un archivo del propio proyecto (el manifiesto, sección 4).
La frase que va en cada reporte: verde significa que cumple convenciones y compila/testea; nunca que sea correcto en el negocio.

Hay otra idea detrás de todo el diseño, y está en los principios del README: cada pieza existe porque el modelo no lo hace solo. Cuando un modelo nuevo lo haga, la pieza se quita.

2

Las piezas de Claude Code sobre las que está construido

El arnés no es un programa aparte: es un conjunto de piezas que Claude Code ya sabe cargar. Vamos una por una.

Plugin y marketplace

Un plugin es un paquete que le agrega cosas a Claude Code (instrucciones, ayudantes, guardias). Un marketplace es una lista de plugins que vive en un repo de git: Claude Code la clona y de ahí instala. El repo agentic-harness es un marketplace con tres plugins:

  • arnes: el arnés de verdad. Funciona completo solo.
  • arnes-ui: un mod de interfaz que muestra en pantalla en qué va el arnés. Opcional.
  • arnes-mod: un mod de comportamiento que todavía no existe (fase 5).

¿Por qué así y no copiando archivos a cada proyecto? Por cómo lee Claude Code su configuración, según la documentación oficial que cita el plan:

  • El archivo de ajustes .claude/settings.json (donde van los guardias y los permisos) solo se lee de la carpeta donde arrancas la sesión. No se hereda de las carpetas de arriba. Si copias los guardias a una carpeta padre, una sesión abierta dentro de un repo hijo no los ve.
  • Un plugin instalado a nivel de usuario carga en todos tus proyectos.
  • Un plugin se fija a una versión (un tag de git, como v0.5.0). Todo el equipo corre la misma versión, y volver atrás es reinstalar el tag anterior. Copiando archivos, cada repo terminaría con su propia variante.

Skill

Una skill es una receta escrita en un archivo corto (SKILL.md): "cuando toque planear, haz esto, en este orden". Claude la lee y la sigue. El arnés trae diez, y todas se llaman con el prefijo del plugin: /arnes:plan, /arnes:verify, etc.

La diferencia importante es quién las puede disparar:

Claude las carga solo

plan, build, verify, review, memory y timeline.

Su descripción empieza con las palabras de un pedido real ("Implementar, corregir o agregar algo…", "Verificar, probar o comprobar…"). Cuando escribes "implementa este issue", Claude reconoce la receta y la carga sin que la nombres. Ese es el truco para que el flujo corra "sin invocar comandos".

Solo las invocas tú

init, ship, worktree y sync.

Llevan disable-model-invocation: true porque mueven ramas, commitean o crean archivos. Claude no puede dispararlas: las escribes tú, por ejemplo /arnes:ship.

Qué hace cada una, en el orden en que aparecen en un issue:

plan Claude solo

Lee el issue (con glab o gh, o el texto que escribiste), revisa las reglas del repo y le pregunta al mapa del código antes de abrir archivos. Escribe .tmp/harness/plan.md con los criterios de aceptación, el contrato de la API, los datos y migraciones, los archivos previstos, las zonas de riesgo y preguntas cerradas con su recomendación. Te lo muestra y espera tu aprobación sin tocar código.

build Claude solo

Construye el plan aprobado, y sin Aprobado: no arranca. Lanza un ayudante dev por workspace, primero el back y después el front, y le pasa al front el contrato del back tal cual. Revisa que cada dev reporte la cobertura de cada criterio y abre algunas de las líneas que cita. Termina con "Construido, sin verificar".

verify Claude solo

Por cada workspace tocado: si hay código nuevo sin test, llama al test-writer. Después corre el gate (ci-gate.js: typecheck contra la foto, lint de los tocados, tests contra la línea base) y escribe la bandera solo si el gate salió con 0.

review Claude solo

La carga ship antes de commitear, una sola vez sobre el diff completo (o tú antes, con /arnes:review): build termina en verify y no la carga, porque el revisor en opus es el gasto grande. Prepara con review.js lo que el revisor necesita, lanza al reviewer una sola vez y marca la revisión con su número de bloqueantes; si ship la repite por cambios posteriores, revisa solo lo que cambió. Si se tocó una zona de riesgo, el reporte empieza con REVISIÓN HUMANA OBLIGATORIA.

ship solo tú

Entrega lo que ya está verificado y revisado. Comprueba la bandera, la revisión sin bloqueantes y que no haya worktrees sin integrar. Usa la misma rama en todos los repos y hace un commit por workspace, el back antes que el front, con la convención del repo. Push y merge request solo con tu sí explícito. Con --solo-commit se detiene después del commit.

memory Claude solo

Tiene tres modos. decision guarda una decisión en docs/decisions/, gotcha anota una trampa conocida en docs/gotchas.md y recall busca lo que ya se decidió. Escribe en markdown dentro del repo y no commitea.

timeline Claude solo

Imprime la cronología del arnés con lo que duró cada etapa, tal como la anotaron las skills y los guardias. Funciona sin el mod de interfaz.

init solo tú

No te pregunta nada: detecta los repos, el stack, los comandos y las rutas de riesgo, escribe el manifiesto de cada repo y la composición de la carpeta, los valida contra el schema y deja lista la adopción en un turno. Al cerrar te dice lo que decidió y lo que no pudo hacer, con su comando. Con --check revisa el mínimo de adopción sin tocar nada.

worktree solo tú

Abre, integra o cierra los worktrees de las tareas de un issue, con su registro. Integrar es un git merge --no-ff en la rama del issue, nunca squash, y después se verifica esa rama.

sync solo tú

Trae a tu rama lo nuevo de origin/main (u otra rama), repo por repo. Antes crea una rama de respaldo, hace fetch y merge (sin squash ni rebase) y lista los archivos que cambiaron los dos lados, que es donde se esconden las incompatibilidades. Después verifica. No hace push, y te deja escrito cómo volver atrás.

Hay un presupuesto: ninguna skill pasa de unas 80 líneas. Hay un test que lo comprueba.

Agente o subagente

Un agente (o subagente) es un ayudante que Claude llama para un trabajo puntual. Arranca con la memoria en blanco, recibe solo lo que Claude le pasa, hace su trabajo y devuelve un reporte. Cada uno tiene sus propias herramientas permitidas y su propio modelo, que es la versión de Claude que lo mueve: opus es la más capaz y la más cara, sonnet va en el medio y haiku es la más rápida y barata.

dev sonnet

El que escribe el código de producción de un solo workspace. Recibe en su entrada las reglas del repo que aplican. No escribe tests.

test-writer sonnet

El que solo sabe escribir tests, y solo para código nuevo o cambiado. No toca código de producción.

reviewer opus

El revisor. Lee (Read, Grep, Glob) y solo escribe su reporte: no tiene terminal ni puede editar código. Trabaja con esfuerzo alto.

¿Por qué un modelo distinto por ayudante? Porque cada trabajo pide algo distinto: escribir un test contra un estándar no necesita al modelo más caro, y juzgar un cambio entero contra una lista de reglas sí lo agradece. Cada agente lleva su model y su effort escritos en su archivo. Y como cada uno tiene su propio contexto, el revisor juzga el árbol de archivos, no el relato de quien lo construyó.

Un detalle del plan: los agentes de un plugin ignoran los campos hooks, mcpServers y permissionMode de su archivo. Por eso todo el control sobre ellos va por los guardias del plugin, no por el agente.

Hook clásico

Un hook es un programa chiquito que Claude Code corre solo en un momento fijo, sin preguntarle al modelo. Recibe un JSON con lo que está pasando y puede responder "agrega este contexto", "no dejes correr esto" o "no termines todavía". En esta página les decimos guardias. El arnés los escribe todos en Node, sin bash, para que corran igual en PowerShell, Git Bash y el CI.

Estos son los momentos (eventos) de una sesión, en orden, y el guardia del arnés que Claude Code dispara en cada uno según hooks/hooks.json. Son ocho guardias en seis eventos: PreToolUse tiene tres, uno por tipo de herramienta.

SessionStart
Cuando abres la sesión (o después de un /clear), antes de que escribas nada.
session-start.js Lee el manifiesto y le inyecta a Claude el estado del proyecto y el protocolo del arnés. Además escribe el candado de la sesión.
UserPromptSubmit
Cada vez que mandas un mensaje, antes de que Claude lo lea.
prompt-context.js Adjunta una línea por workspace con lo tocado, si la bandera está vigente y si se tocó una zona de riesgo. También saca la foto del turno. Nunca bloquea.
PreToolUse
Justo antes de que Claude use una herramienta. Aquí se puede negar.
guard.js Antes de cada comando de Bash o PowerShell: niega git destructivo, leer secretos con cat y compañía, lo que el manifiesto marca como forbidden y un git commit sin bandera.
read-guard.js Antes de Read, Glob o Grep: niega abrir o buscar en archivos de secretos.
worktree-remove.js Antes de ExitWorktree: niega borrar un worktree con commits sin integrar.
PostToolUse
Justo después de que la herramienta terminó.
after-edit.js Después de cada Edit o Write: pasa el lint por el archivo editado y le devuelve a Claude lo que encontró. Nunca bloquea.
Stop
Cuando Claude quiere terminar su respuesta y devolverte el turno. Aquí se le puede decir "todavía no".
stop-gate.js Bloquea una vez por turno si quedó código sin verificar o worktrees con commits sin integrar.
SessionEnd
Cuando cierras la sesión.
session-start.js El mismo script del arranque: aquí borra el candado de la sesión.

El detalle de cada uno (qué mira, qué bloquea y qué nunca bloquea) está en la sección 6.

Un turno es todo lo que pasa entre que mandas un mensaje y Claude te devuelve el control: pueden ser muchos pasos con herramientas en medio. Los hooks no piden permiso: corren fuera del sistema de permisos.

Mod

Un mod es otro tipo de enganche, más nuevo y más poderoso. En vez de un programa que corre en un momento fijo y responde un JSON, es un módulo de código que se mete dentro de Claude Code y puede envolver casi todo: cada herramienta antes y después, cada respuesta del modelo, el texto que ve el modelo, y la pantalla (paneles, una banda, la línea de estado, avisos).

  • Hook clásico: un comando suelto que mira y decide en un momento fijo. Es lo que usa el arnés para todo lo que debe cumplirse.
  • Mod: código que vive dentro de la sesión, escucha muchos eventos y puede dibujar. Solo carga en sesiones locales.

¿Por qué el de interfaz va aparte? Para que lo visual no comparta destino con lo que gobierna el flujo. arnes-ui tiene una regla única: cada enganche observa y deja pasar el evento tal como venía, sin tocar nada. Si se cae, se apaga o no está instalado, el arnés hace exactamente lo mismo.

¿Por qué puede fallar sin romper nada? Porque cada enganche del mod atrapa sus propios errores, los anota en el transcript con $.ui.log y deja pasar el evento original. Y porque nada que importe depende de él: la medición de tiempos la escriben las skills en un archivo (.tmp/harness/timeline.jsonl) que existe aunque el mod no esté.

Esto no es teoría. En las pruebas, un plugin interno de Claude Code (cc-plugin-sec-default) se saltó dos enganches del mod: el del Stop y el de carga de skills. La banda dejó de mostrar algunas etapas, y el arnés siguió igual. La corrección fue sacar esas etapas de la timeline, que ya existía.

4

El manifiesto: .claude/harness.json

El manifiesto es un archivo JSON que le dice al arnés cómo es tu proyecto: qué comandos corre para revisar tipos, lint y tests, dónde están las zonas de riesgo y qué comandos están prohibidos. El arnés no adivina nada del stack: si algo no está en el manifiesto (o en el CLAUDE.md del repo, que es el archivo de reglas que Claude lee al trabajar ahí), no existe.

Hay dos tipos, y el schema acepta exactamente uno de los dos en cada archivo:

  • De repo (<repo>/.claude/harness.json): lleva workspaces con sus comandos. Es el que lee el CI de ese repo, que clona solo ese repo.
  • De composición (<carpeta>/.claude/harness.json): para una carpeta que tiene varios repos adentro. Lleva repos, los lista y agrega solo lo que existe entre repos. Los comandos no se repiten ahí.

Un workspace es una parte del proyecto con sus propios comandos: en una carpeta con varios repos, cada repo es un workspace.

Un manifiesto de repo, línea por línea

Este es el de la prueba con api-academico, recortado:

"version": 1,
La versión del formato del manifiesto.
"name": "api-academico",
El nombre del proyecto.
"workspaces": [ {
La lista de partes con comandos. En un repo normal hay una sola.
"name": "api-academico", "path": ".", "git": ".",
El nombre del workspace, su carpeta dentro del repo y dónde está la raíz de git. . es "aquí mismo".
"defaultBranch": "main", "stack": "nestjs-prisma",
La rama principal. stack es solo una etiqueta: el arnés nunca decide nada por ella.
"commands": { "typecheck": ["npx tsc --noEmit"], "lint": "npx eslint {files} --max-warnings=0 --no-warn-ignored", "test": "npx jest {specs} --runTestsByPath --verbose", "testAll": "npx jest" },
Los comandos reales del repo. {files} se reemplaza por los archivos tocados y {specs} por los tests elegidos. El typecheck es una lista porque Angular necesita dos. Todo es opcional salvo tener typecheck o test.
"specPattern": "{dir}/{name}.spec.ts",
Dónde vive el test de un archivo: misma carpeta, mismo nombre, terminado en .spec.ts. Así se eligen solo los tests de lo que tocaste.
"riskPaths": ["prisma/migrations/**", "src/modules/auth/**", "src/common/constants/acl*.ts"],
Las zonas de riesgo. Tocar un archivo que caiga aquí obliga a la revisión humana. Esto lo completa la persona al adoptar: el arnés no lo infiere.
"forbidden": ["npm run lint", "npm run format", "prisma migrate reset"]
Comandos que el guardia niega en este repo: reescriben archivos en masa o son destructivos.
} ], "integration": { "branchPrefix": "feature/" },
El prefijo de las ramas que crea ship.
"memory": { "notes": "docs/decisions", "gotchas": "docs/gotchas.md", "graphify": true }
Dónde se escriben las decisiones y las trampas conocidas, y si el repo tiene mapa de graphify (sección 10).

Hay campos opcionales que también leen los guardias: codeGlobs (qué cuenta como código; por defecto .ts, .tsx, .js, .jsx, .php y .sql, nunca .md), sharedPaths (código compartido que obliga a correr todos los tests), secretPaths (más archivos de secretos) y commands.typecheckFast (un typecheck rápido para después de cada edición).

Una composición de carpeta

{
  "version": 1,
  "name": "academico",
  "repos": [
    { "path": "api-academico", "contract": { "provides": ["src/**/dto/**", "src/**/*.controller.ts"] } },
    { "path": "academico-front", "contract": { "consumes": ["src/**/types/**", "src/**/api/**"] } },
    { "path": "academicoBitbuckett" }
  ],
  "integration": { "branchPrefix": "feature/", "sameBranchAcrossWorkspaces": true }
}
  • repos lista los repos por carpeta. Cada uno se lee de su propio .claude/harness.json.
  • contract dice qué archivos de un repo forman la API que otro consume: el back provee los DTO y los controladores, el front consume los tipos y el cliente de la API. El revisor usa esto para detectar un contrato roto.
  • sameBranchAcrossWorkspaces: la misma rama en todos los repos del issue.

Cómo se encuentra: los scripts suben desde la carpeta donde está Claude hasta el primer manifiesto. Si es de repo, siguen subiendo por si una composición lo lista. Así una sesión abierta dentro de api-academico/ sigue viendo a sus hermanos, y el CI, que no tiene carpeta encima, ve solo su repo.

Adoptado y no adoptado

En el ejemplo, academicoBitbuckett (un repo PHP) aparece sin contract y no tiene manifiesto propio. Eso lo deja como no adoptable todavía: los scripts lo ven, lo muestran al arrancar ("no adoptable todavía: sin manifiesto propio, no se verifica"), pero no lo verifican ni lo bloquean. No es un error.

Un repo adoptado es uno que tiene su manifiesto y cumple el mínimo de adopción: ocho comprobaciones que corre /arnes:init --check (sección 14).

La historia completa de un issue

Un issue es un pedido de trabajo (en GitLab o GitHub, o escrito a mano). Este es el recorrido real del CRUD de talleres de docs/PRUEBA-FASE-3.md, hecho sobre un clon de api-academico el 2026-10-20. Los tiempos son los de la prueba manual en una sesión interactiva; donde sirve, se cuenta también lo que pasó en la corrida automática de ese mismo día.

Cada paso dice quién lo hizo: la persona Claude solo un ayudante un script que no piensa

Lo que escribe la persona, sin comandos
Implementa este issue: CRUD de talleres: listar, crear, editar y eliminar talleres; el modelo Taller ya existe en el esquema de Prisma; solo roles ADMIN y COORDINADOR pueden crear y eliminar; un taller con alumnos inscritos no se elimina, se desactiva.

Puedes usar las flechas del teclado cuando la historia tenga el foco. La timeline de la prueba manual cerró con plan 16m01s · build 8m13s · verify 4m21s · review 2m05s · ship 19s.

6

Los guardias, que son los hooks

Una tarjeta por cada entrada de plugins/arnes/hooks/hooks.json, sacada de los scripts de scripts/hooks/. Dos reglas valen para todos:

  • Leen la carpeta donde está Claude del JSON que reciben, nunca de una variable fija: así siguen a Claude dentro de un worktree.
  • Si un guardia se rompe por un error propio, sale con 0 y no actúa: un guardia roto nunca bloquea la sesión. El error queda en el log.

El de arranque de sesión

SessionStart · session-start.js

Cuándo
Al abrir la sesión, y después de un /clear.
Qué mira
El manifiesto; la rama y los archivos sin commitear de cada workspace; los worktrees sin integrar del registro (cinco como máximo, con aviso a los de más de 7 días sin commits nuevos); las cinco decisiones más recientes; y si hay otra sesión de Claude viva en el mismo proyecto, con un "candado" propio en .tmp/harness/sessions/.
Qué hace

Qué bloquea
Nada: solo informa.

El de cada mensaje

La bandera

La bandera (o bandera de verificación) es un archivito que dice "este workspace, tal como está ahora, pasó la verificación". Es lo que pide el guardia antes de dejarte commitear.

Quién la escribe

Solo /arnes:verify, con gate-flag.js write, y solo si el gate salió con código 0. La skill lo dice así: nunca escribas pass porque la salida "parece" verde; el código de salida decide.

Dónde vive

.tmp/harness/gate/<workspace>.json, en la raíz del proyecto. No se commitea.

Qué guarda

{ "head": "…", "touchedHash": "…", "contentHash": "…", "result": "pass", "at": "2026-10-20T…" }
  • head: el commit en que estaba el repo.
  • touchedHash: una huella de la lista de archivos tocados. Una huella (hash) es un código corto que cambia si cambia cualquier cosa de lo que resume.
  • contentHash: una huella del contenido de cada archivo tocado, trackeado o no.
  • result y at: el resultado y la hora.

Cuándo vence

Vale solo si se cumplen todas: dice pass, el HEAD es el mismo, la lista de tocados es la misma, y el contenido de cada tocado es el mismo; no vence por tiempo. Cambias una coma en un archivo tocado y se vence. Haces un commit y se vence (cambió el HEAD).

El contentHash entró en la fase 2b: la prueba manual mostró que editar un archivo ya tocado no vencía la bandera.

Por qué un commit sin bandera se niega

Porque es la única manera de que "verifiqué" no dependa de la palabra de Claude. El guardia de comandos, ante un git commit, consulta la bandera del workspace; si no está vigente, lo niega con el motivo y le dice que verifique con /arnes:verify. Por eso ship hace un solo commit por workspace: el primer commit cambia el HEAD y vence la bandera.

La huella cubre solo los archivos tocados, no el árbol entero. Fue a propósito (está en la lista de lo que no se hace): la garantía de verdad es el CI, que corre lo mismo sobre el merge request. La bandera es un marcador de la sesión, no un sello.

La verificación sin trampas

El problema típico: el repo ya tiene errores viejos de tipos o tests rojos de antes. Si verificar es "todo en verde", nunca pasa; si es "más o menos verde", cualquier cosa pasa. El arnés compara contra lo que había antes, con tres piezas.

La foto de typecheck, por diagnóstico

Un typecheck es el programa que revisa que los tipos cuadren (en TypeScript, tsc). Un diagnóstico es cada error que reporta.

  • ci-gate.js saca una foto del commit de base con git archive en una carpeta temporal (no toca .git, no crea ramas), corre el typecheck ahí y lo compara con el de tu árbol.
  • Cada diagnóstico se identifica por archivo + código de error + primera línea del mensaje, sin línea ni columna: si mueves código, los errores viejos desplazados no cuentan como nuevos.
  • Se comparan conteos, no listas: un tercer error idéntico a dos que ya había es nuevo.
  • La foto queda en .tmp/harness/typecheck/<ws>.txt y se reutiliza mientras el HEAD no cambie. En la prueba: typecheck ok · sin diagnósticos nuevos (base 0, ahora 0) · foto del base reutilizada.

La línea base de tests, commiteada

La línea base es un archivo commiteado en el repo (tests/baseline.json) que guarda, por cada archivo de test (spec), cuántos tests pasan, cuántos fallan y cuántos se saltan, y los saltos por nombre.

  • Verify corre solo los specs de lo que tocaste, y compara su suma contra la suma de esos mismos specs en la base.
  • Por qué un test borrado pone rojo: si hay menos tests que en la base, aunque los que quedan estén verdes, es una regresión silenciosa. Borrar o saltar un test es la forma más fácil de "arreglar" un rojo, y esto la cierra. Un spec de la base que ya no existe también es rojo, haya o no otro código tocado.
  • Recapturar la base es decisión de la persona, nunca de Claude para que cuadre, y su commit lleva el prefijo gates:.

Los rojos conocidos, con fecha

Los tests que ya fallaban van en tests/known-failures.txt, uno por línea:

2026-08-27 | src/modules/horario-sede/horario-sede.service.spec.ts | <nombre completo del test>
  • Solo cuenta la coincidencia exacta de spec y nombre. Esas fallas no ponen rojo y salen en el reporte como preexistente (2026-08-27).
  • Una línea sin fecha no absuelve.
  • La lista es temporal: si una suite está rota, el issue es arreglarla. En api-academico eran 18 fallas de 5.279 tests en 314 specs.

Por qué el CI corre lo mismo que la sesión

Verify corre ci-gate.js --ws <ws> --base HEAD, y el CI corre el mismo ci-gate.js con la base del merge request. Mismo motor, misma clave de diagnósticos, misma línea base, mismos rojos conocidos. Lo que pasa en tu sesión pasa en el pipeline, y si alguien se salta la sesión (o el arnés se equivoca), el pipeline lo atrapa. Ese es el seguro real.

Hay cosas que ni tsc ni jest ven. En la prueba: mover TallerRepository a otro módulo de inyección de dependencias. Para eso hace falta arrancar la app con base de datos, y hoy está como decisión abierta (un posible commands.boot).

Los worktrees

Un worktree es una segunda carpeta de trabajo del mismo repo, en otra rama, sin clonar de nuevo. Sirve cuando dos ayudantes del mismo issue tocarían los mismos archivos a la vez, o cuando ya hay otra sesión trabajando en tu árbol: cada uno trabaja en su carpeta y después se junta.

El problema que se vio antes del arnés: en renova365 había 12 worktrees huérfanos en api/. Cada ayudante deja su rama y nadie se acuerda de integrarla.

Cuándo no usarlos: si los ayudantes tocan archivos distintos, trabajan en el mismo árbol, uno tras otro o en paralelo, sin ramas. Cero integración.

El registro y las ramas efímeras

  • Solo la skill /arnes:worktree (que corre la persona) abre, integra y cierra, sobre worktree-ledger.js.
  • El registro (ledger) es .tmp/harness/worktrees.json: por cada worktree, su workspace, carpeta, rama, destino, issue, fecha y estado (abierto, integrado o cerrado).
  • Cada tarea va en una rama efímera, que existe solo mientras dura la tarea: wt/<rama-del-issue>/<slug>, creada desde la rama del issue, nunca desde main. Por ejemplo wt/feature/crud-talleres/taller-select-activos. Con ese nombre, git dice mecánicamente qué falta integrar.
  • Los worktrees viven en .tmp/harness/worktrees/<ws>/<slug>.
  • integrate hace git merge --no-ff en la rama del issue (nunca squash: el squash lo hace GitLab al mergear a main), borra el worktree y la rama, y cierra el registro. Después se verifica la rama del issue.
  • close cierra solo un worktree sin commits propios. Con commits, se niega.

Por qué nada se queda sin integrar: los cuatro cercos

Un ayudante "terminó" solo cuando su rama ya no existe. Si algo se salta ese paso, lo atajan cuatro cercos:

  1. El Stop bloquea una vez el turno que dejó commits sin integrar en un worktree del issue.
  2. El arranque de sesión lista los pendientes al abrir, y avisa de los que llevan más de 7 días sin commits nuevos: "intégralo o ciérralo, nunca se borra solo".
  3. Ship se niega a commitear o abrir el merge request si hay worktrees del issue abiertos.
  4. Borrar un worktree con commits sin integrar se niega, tanto por la herramienta ExitWorktree como por git worktree remove en la terminal.

Antes del primer cerco está el aviso de sesión concurrente: si otra sesión ya trabaja en el mismo proyecto, la nueva recibe "esta sesión debe trabajar en su propio worktree".

Limitación de esta versión: los worktrees que abre el registro no copian .env ni enlazan node_modules. Para verificar dentro de uno hay que instalar dependencias. Queda para los templates de la fase 6.

La memoria y el mapa

El mapa: graphify

graphify es una herramienta externa que arma un grafo del código: un mapa de qué archivo, clase o función se relaciona con cuál. Vive en graphify-out/graph.json de cada repo.

  • Qué guarda: al principio, solo código (GRAPHIFY_BACKEND=none). Se reconstruye en cada commit o checkout con su propio hook de git. El reporte graphify-out/GRAPH_REPORT.md se versiona; el graph.json, según su tamaño.
  • Qué no guarda: las decisiones del equipo (eso va en markdown, abajo), y por ahora tampoco la lectura semántica de los documentos: cuándo activarla es una decisión abierta.
  • Cómo lo consulta el plan: si el repo tiene el grafo y el comando responde, el plan le pregunta antes de abrir archivos (graphify query, explain y path) y abre solo las líneas que el grafo ubicó, en vez de barrer el repo. Sin graphify, busca por los nombres del issue y abre un módulo parecido. En la prueba, el plan consultó el grafo y descubrió que el modelo es taller en minúsculas, que las inscripciones son usuario_taller y que el acceso va por permisos, no por nombre de rol.

Las decisiones y los gotchas, en markdown

La skill memory escribe dos cosas dentro del repo:

  • Decisiones: docs/decisions/AAAA-MM-DD-<slug>.md, con Qué, Por qué y Alternativa descartada. Si falta el porqué o la alternativa, lo pregunta en un mensaje; no lo inventa.
  • Gotchas: un gotcha es una trampa conocida. Van en docs/gotchas.md, una línea cada uno: - fecha · workspace · síntoma → causa → qué hacer.
  • Recall: buscar lo ya decidido, con búsqueda de texto en esos archivos y en graphify. No escribe nada.

El arranque de sesión muestra los títulos de las cinco decisiones más recientes.

¿Por qué en archivos y no en una base local? Porque así es visible para todo el equipo y para los merge requests, viaja con el repo, se revisa como código y no depende de ningún servidor ni MCP (un MCP es un servidor de herramientas extra que se le conecta a Claude). Engram, que es una memoria personal en una base local, queda opcional: el arnés no depende de él.

Ojo al adoptar: en las ramas de trabajo de api-academico el .gitignore ignora docs, así que una decisión no se versiona sin git add -f. La skill lo avisa.

Un comando de barra es lo que escribes en el chat de Claude Code empezando con /. Cada skill del arnés es uno, con el prefijo /arnes:. Lo que va entre < > es obligatorio, lo que va entre [ ] es opcional y | separa opciones. Los argumentos salen del argument-hint de cada SKILL.md.

/arnes:review

  • Push y merge request solo con tu sí explícito.
  • --solo-commit: se detiene después del commit.
  • <rama>: el nombre de la rama; si no lo das, usa la que propone el chequeo. El prefijo del manifiesto se agrega solo.

Ejemplo de la prueba: /arnes:ship --solo-commit.

/arnes:worktree solo tú

  • open: abre un worktree por repo (o los de --ws) en wt/<rama-issue>/<slug>.
  • integrate: merge --no-ff en la rama del issue, borra el worktree y la rama, cierra el registro.
  • close: cierra uno sin commits propios.
  • list muestra los abiertos (list --all, también los cerrados); pending muestra lo que falta integrar.

Ejemplo de la prueba: /arnes:worktree open taller-select-activos --issue "CRUD de talleres".

/arnes:sync [rama] [--ws <workspace>]...

Trae a tu rama lo nuevo de origin/<rama> (por defecto, la rama principal de cada workspace): respaldo, fetch, merge sin squash ni rebase, la lista de lo que cambiaron los dos lados y verify. No hace push. Volver atrás lo haces tú en tu terminal con git reset --hard <respaldo>, porque el guardia no se lo deja a Claude.

/arnes-panel

Abre o cierra el panel de arnes-ui. No lleva arnes: porque un comando que registra un mod no lleva prefijo de plugin. Solo existe si el mod está instalado.

Los de Claude Code que aparecen en el flujo

  • /hooks: lista los hooks que cargó la sesión. Sirve para comprobar que los del arnés están.
  • /clear: limpia la conversación. Vuelve a correr el arranque, así que el contexto del arnés se inyecta de nuevo.
  • /exit: cierra la sesión; corre el de fin de sesión, que suelta el candado.
  • /cost: el costo total de la sesión. De ahí salen las restas que hace el mod para el costo por etapa.

Los scripts, para la terminal

Debajo de las skills hay scripts en Node que también puedes correr tú desde la terminal, con node "<carpeta del plugin>/scripts/<script>.js". Todos aceptan --help, que imprime su uso y sus códigos de salida. En general los corren las skills; los marcados con ★ son los que más te pueden servir a ti para mirar el estado.

lib/manifest.js validate [archivo] | which <ruta> | show
★ Valida un manifiesto, dice a qué workspace pertenece una ruta, o muestra el proyecto resuelto.
adoption-check.js [--ws <nombre>]...
★ Las ocho comprobaciones del mínimo de adopción. Es lo que corre /arnes:init --check.
gate-flag.js check <ws>
★ Dice si la bandera está vigente y, si no, por qué. El write lo usa verify: nunca se escribe a mano.
worktree-ledger.js list [--all] | pending [--target <rama>]
★ Los worktrees del registro y lo que falta integrar. open, integrate y close van por /arnes:worktree.
lib/timeline.js print
★ La cronología, igual que /arnes:timeline. start, end y note los escriben las skills.
test-baseline.js capture <ws> | check <ws> [--base <ref>] [spec ...]
★ Captura la línea base de tests (decisión tuya; su commit lleva gates:) o compara contra ella.
ci-gate.js [--ws <nombre>]... [--base <ref>]
El gate completo: lo que corre el CI y verify. Sale con 0 en verde y con 1 en rojo.
touched-files.js [--ws] [--base] [--ext] [--relative] [--workspaces]
Los archivos tocados por workspace.
test-select.js --ws <nombre> [--base] [--missing] [archivo ...]
Los specs de lo tocado, o con --missing, el código nuevo sin spec.
typecheck-baseline.js capture|diff <ws> <ref> <foto>
La foto de typecheck y su comparación por diagnóstico.
review.js input [--completa] | mark --blockers <n> | check
La entrada del revisor, la marca de revisión hecha y su comprobación.
ship.js check | branch <rama> | stage <ws>
Lo determinista de ship: el chequeo, la rama y el stage.
merged-files.js [--ws] [--ref <commit>] [--json]
Lo que de verdad se combinó en un merge. Lo usa sync.
init-draft.js [--write] [--force]
Los borradores de manifiesto que usa /arnes:init.

Los códigos de salida siguen una convención casi común a todos: 0 es bien, 1 es "no" (rojo, no vigente, no listo) y 2 es uso inválido o sin manifiesto. Cada script la detalla en su --help.

Cómo instalar y cómo adoptar un repo

Instalar

El repo vive en GitLab. La forma corta owner/repo siempre apunta a github.com, así que va la URL completa con el tag al final:

claude plugin install arnes --marketplace https://gitlab.com/preupdv/apps/agentic-harness.git#vX.Y.Z
claude plugin install arnes-ui@agentic-harness
claude plugin install arnes-mod@agentic-harness
  • El primero añade el marketplace fijado a ese tag e instala arnes. Los otros dos son opcionales.
  • Claude Code clona con git sin preguntar credenciales: la de GitLab tiene que estar guardada antes (Git Credential Manager), o usar la forma SSH git@gitlab.com:preupdv/apps/agentic-harness.git#vX.Y.Z.
  • Para fijar la versión en un repo, va en su .claude/settings.json (extraKnownMarketplaces con el ref del tag y enabledPlugins).
  • El auto-update viene apagado y se deja así.

Permisos recomendados

Sin ellos el arnés funciona igual, pero pregunta a cada rato. Van en ~/.claude/settings.json, en permissions.allow:

  • los node de los scripts del plugin, con la ruta de la caché de plugins;
  • git de lectura (status, diff, log, show, rev-parse, ls-files, merge-base);
  • los comandos de typecheck, lint y test del manifiesto;
  • las consultas de graphify y la lectura del issue con glab o gh.

Y una regla ask para npx eslint *--fix*, que se evalúa antes y obliga a preguntar. git commit y git push quedan fuera a propósito. La lista completa está en el README.

Adoptar un repo

  1. Quitar los hooks del arnés anterior del .claude/settings.json del repo (y de la carpeta, si tiene). Si no, pelean con los del plugin. /arnes:init los quita solo.
  2. Correr /arnes:init: detecta los repos, el stack, los comandos y el formato de los tests, y escribe el manifiesto de cada repo y la composición sin preguntar: lo que antes te consultaba (riskPaths, contract, integration) lo decide y te lo dice al cerrar, y una corrección se la pides en un mensaje. Nunca inventa comandos. Valida cada archivo contra el schema. No commitea ni hace push.
  3. Correr /arnes:init --check: el mínimo de adopción. No modifica nada.

El mínimo de adopción son ocho comprobaciones:

  1. Manifiesto válido contra el schema.
  2. CLAUDE.md con reglas duras del stack (200 líneas como máximo) y .claude/rules/ con paths:.
  3. Typecheck y lint que corren, sin --fix.
  4. Un job de CI que corre ci-gate.js y bloquea el merge request si falla; merge solo con pipeline en verde, squash al mergear a main y detección de secretos.
  5. riskPaths declaradas y regla de aprobación en GitLab o Bitbucket.
  6. El plugin fijado a un tag.
  7. Ningún hook del .claude/settings.json corre scripts propios de .claude/hooks/.
  8. La línea base de tests commiteada, con los saltos declarados por nombre.

Cada una sale como ok, FALTA, MANUAL (configuración del host git que no se puede ver desde tu máquina) o NO ADOPTABLE (un repo sin manifiesto propio). Solo FALTA cuenta como falta.

Versionado por tags

  • Un tag vX.Y.Z del repo cubre los tres plugins, con su entrada en el CHANGELOG. Es lo que fija el equipo.
  • El campo version del plugin.json de cada plugin va igual al tag. Claude Code compara ese campo, no los commits: pushear código sin subirlo no le llega a nadie.
  • Subir o bajar de versión es quitar el marketplace (claude plugin marketplace remove agentic-harness, que desinstala sus plugins) y añadirlo en el otro tag.
  • El CLI de Claude Code y el arnés se suben juntos, nunca uno solo. El README trae la tabla de qué tag se probó con qué versión del CLI: v0.5.0 con 2.1.304 y Node 24.

Limitaciones conocidas de esta versión

  • arnes-mod no existe todavía: hoy el protocolo llega por el arranque de sesión y la revisión depende de que Claude cargue la skill.
  • Un plugin interno de Claude Code se salta los enganches classic.Stop y skill.prompt de los mods. El mod ya no depende de ellos, pero es un hecho de la plataforma, no del arnés.
  • Que un toast se vea depende de dónde corras Claude Code; los avisos importantes van también al transcript.
  • El mod no puede calcular la vigencia exacta de la bandera (no ve la carpeta del otro plugin): la muestra vencida si un archivo cambiado se modificó después. Quien decide de verdad son el guardia y el Stop.
  • El costo por ayudante es inexacto con ayudantes en paralelo.
  • Los worktrees no copian .env ni enlazan node_modules.
  • Lo que ni tsc ni jest ven (como un cambio de inyección de dependencias) no se detecta sin arrancar la app.
  • La bandera cubre solo los archivos tocados; la garantía de todo el árbol es el CI.
  • El texto corrupto de la línea Plan: que se vio en la prueba (Plnd CRUD dw talleres) no se pudo reproducir; se quitaron sus causas conocidas y se confirma en la próxima prueba manual.
  • Lanzar claude -p desde una sesión depende de cómo lo juzgue el modo de permisos.

Cómo reportar un problema

El repo vive en GitLab, en gitlab.com/preupdv/apps/agentic-harness. La guía de prueba pide reportar así: por cada paso, si salió como está escrito, y si no, el texto exacto que viste. No son fallos los conteos o fechas distintos porque las ramas avanzaron, ni que el plan, el dev o el revisor redacten distinto. Sí son fallos:

  • tener que invocar plan, build, verify, review o memory para que corran;
  • una bandera escrita con un paso en rojo;
  • un revisor con terminal, o que edite archivos;
  • un ship que commitee sin bandera vigente, con bloqueantes o con worktrees del issue sin integrar;
  • un push fuera de donde debía ir.

Si te sirve para el reporte, /arnes:timeline te da la cronología tal cual.

Preguntas de alguien escéptico, con respuestas honestas

¿Me va a cambiar código sin avisar?

Antes de tocar código, no: el plan se escribe, se te muestra y espera tu respuesta. La skill lo dice literal: no edites código ni lances agentes antes de esa respuesta. Y build se niega a arrancar si el plan no dice Aprobado:.

Después de que apruebas, sí edita archivos de tu árbol sin pedirte permiso por cada uno: ese es el trabajo. Lo que no hace es commitear: eso solo pasa con /arnes:ship, que solo puedes invocar tú. Al final te dice qué tocó (con archivo:línea por criterio) y que no hizo commit. Si algo no te gusta, está todo en tu árbol sin commitear.

¿Puede hacer push o borrar algo?

El guardia de comandos niega siempre git reset --hard, el push forzado, git clean -f, borrar una rama o un worktree con commits sin integrar, y leer secretos. Eso vale aunque no haya manifiesto.

Un push normal no lo niega el guardia: lo frena que ship pide un sí explícito antes de cualquier push o merge request, nunca usa --force, y que git push no está en los permisos recomendados, así que Claude Code te pregunta. En la prueba, además, el push estaba denegado y todo corría contra un repo de mentira en .tmp.

Lo honesto: el guardia no juzga un borrado de archivos común (un rm, por ejemplo). Eso queda en los permisos de Claude Code, como sin el arnés. Lo que sí no se pierde son los commits: ni las ramas ni los worktrees con trabajo sin integrar se dejan borrar.

¿Qué pasa si me equivoco en el plan?

Antes de aprobar, pides cambios y el plan se ajusta (y vuelve a esperar), o lo descartas. Las preguntas son cerradas y cada una trae una recomendación con su motivo y una alternativa real con lo que cuesta.

Si apruebas algo equivocado, el arnés lo va a construir bien hecho y en verde. El revisor comprueba que el código cumpla los criterios del plan, no que el plan sea correcto para el negocio. Por eso el plan está escrito para que lo apruebe alguien que no conoce el stack: frases cortas, cada término técnico explicado. Ejemplo real: el issue pedía "solo ADMIN y COORDINADOR". El plan lo tradujo a permisos taller.*, porque las reglas del repo prohíben comparar nombres de rol, y dejó pendiente otorgarlos en el mantenedor de roles. Esa clase de decisión es la que tienes que leer.

¿Cuánto cuesta una corrida?

El único número medido es el de la corrida automática del CRUD de talleres: $13.36 en seis turnos, con estos repartos por etapa: plan $1.43, build $1.44, verify $1.95, review $3.93 y ship $0.36. Fuera de toda etapa quedaron $4.26 (la aprobación, el catálogo de permisos, las correcciones entre rondas y los reportes). Esa corrida tuvo tres rondas de revisión, y review fue la etapa más cara.

De la prueba manual hay tiempos pero no un costo anotado en la guía. Con arnes-ui ves el costo de cada etapa y de cada ayudante mientras pasa, y el promedio de las últimas corridas. Medir esto es justo lo que va a hacer el piloto.

¿Y si el arnés se cae?
  • Si un guardia tiene un error propio, sale con código 0 y no actúa: un guardia roto nunca bloquea la sesión. El error queda en el log.
  • Si el mod de interfaz falla, anota el error en el transcript y deja pasar todo; el arnés sigue igual. Y el arnés funciona completo sin el mod.
  • Si no hay manifiesto (o no valida), el arnés no verifica ni bloquea nada, salvo git destructivo y la lectura de secretos, y te dice cómo arreglarlo.
  • Si el arnés deja pasar algo que no debía, el CI corre los mismos scripts sobre el merge request y bloquea el merge si falla. Esa es la red de abajo.

Glosario

Adoptado
Un repo con su propio manifiesto que cumple el mínimo de adopción que revisa /arnes:init --check.
Agente / subagente
Un ayudante que Claude llama para un trabajo puntual, con su propio contexto, sus herramientas y su modelo. El arnés trae dev, test-writer y reviewer.
Arnés
Lo que se le pone alrededor a Claude Code para que trabaje siempre igual: recetas, ayudantes, guardias y scripts.
Bandera
El archivo .tmp/harness/gate/<ws>.json que dice que un workspace, tal como está, pasó la verificación. Vence con cualquier cambio, no por tiempo. Sin ella no hay commit.
Bloqueante
Un hallazgo del revisor que cae en la lista cerrada de reglas. Con bloqueantes, ship no entrega.
CI
El servidor (en GitLab, el pipeline) que vuelve a correr las comprobaciones cuando subes un cambio. Corre el mismo ci-gate.js que la sesión.
Claude Code
Claude trabajando en tu terminal: lee, edita y corre comandos.
CLAUDE.md
El archivo de reglas de un repo que Claude lee al trabajar ahí.
Comando de barra
Lo que escribes en el chat empezando con /, como /arnes:ship. Cada skill del arnés es uno.
Composición
El manifiesto de una carpeta con varios repos: los lista y agrega solo lo que existe entre ellos (contrato e integración).
Contrato
Los archivos que forman la API que un repo provee y otro consume. Romperlo sin cambiar el otro lado es bloqueante.
Diagnóstico
Cada error que reporta el typecheck.
Evento
Un momento fijo de la sesión en que corren los hooks: SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop y SessionEnd.
Foto de typecheck
El resultado del typecheck sobre el commit de base, guardado para comparar contra tu árbol por diagnóstico.
Gate
La verificación de ci-gate.js: typecheck, lint y tests contra la base. Verde o rojo según su código de salida.
Gotcha
Una trampa conocida, anotada en docs/gotchas.md con síntoma, causa y qué hacer.
graphify
Herramienta externa que arma un mapa del código de cada repo, que el plan consulta antes de abrir archivos.
Grafo
Un mapa de qué cosa del código se relaciona con cuál.
Hook
Un programa chiquito que Claude Code corre solo en un evento fijo, sin preguntarle al modelo. En esta página, un guardia.
Huella (hash)
Un código corto que cambia si cambia cualquier cosa de lo que resume.
Issue
Un pedido de trabajo, en GitLab o GitHub o escrito a mano.
Línea base de tests
tests/baseline.json, commiteado: cuántos tests pasan, fallan y se saltan por spec. Tener menos tests que ahí es rojo.
Manifiesto
.claude/harness.json: el archivo que le dice al arnés los comandos, las zonas de riesgo y lo prohibido de un repo.
Marketplace
Una lista de plugins que vive en un repo de git y de donde Claude Code instala.
MCP
Un servidor de herramientas extra que se le conecta a Claude. El arnés no depende de ninguno.
Mod
Un módulo de código que vive dentro de Claude Code y puede envolver casi cualquier evento y dibujar en pantalla. arnes-ui es uno.
Modelo
La versión de Claude que mueve a un agente: opus (la más capaz), sonnet (el medio) o haiku (la más rápida y barata).
No adoptable todavía
Un repo listado en la composición sin manifiesto propio: se ve, pero no se verifica ni bloquea.
Plugin
Un paquete que le agrega skills, agentes y hooks a Claude Code, fijado a una versión.
Rama efímera
La rama wt/<rama-issue>/<slug> de un worktree, que existe solo mientras dura la tarea.
Registro (ledger)
.tmp/harness/worktrees.json: la lista de worktrees abiertos, integrados y cerrados.
Revisión humana obligatoria
La marca que sale cuando se tocó una zona de riesgo: una persona tiene que leer ese cambio.
Rojos conocidos
Los tests que ya fallaban, en tests/known-failures.txt con fecha. No ponen rojo; solo cuentan si coinciden exacto.
Skill
Una receta escrita en un archivo corto que Claude lee y sigue. Unas las carga Claude solo; otras solo las invocas tú.
Spec
Un archivo de tests, como taller.service.spec.ts.
Tag
Una etiqueta de git que fija una versión, como v0.5.0.
Timeline
.tmp/harness/timeline.jsonl: una línea por inicio, fin o nota de cada etapa. Existe sin el mod.
Turno
Todo lo que pasa entre que mandas un mensaje y Claude te devuelve el control.
Typecheck
El programa que revisa que los tipos cuadren; en TypeScript, tsc.
Workspace
Una parte del proyecto con sus propios comandos; en una carpeta multi-repo, cada repo.
Worktree
Una segunda carpeta de trabajo del mismo repo, en otra rama, sin clonar de nuevo.
Zona de riesgo (riskPaths)
Rutas declaradas en el manifiesto cuyo cambio exige revisión humana: migraciones, autenticación, permisos.
